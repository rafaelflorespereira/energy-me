Energy Me / Architecture proposal

Save one check-in per user, per day.

Keep Cognito for identity. Put a small authenticated API in front of DynamoDB. Store the seven feelings under stable English keys and preserve their 0-4 scale.

Documentation only. No backend resources or application behavior changed.

One tableNo separate users or feelings tables.
One record per dayThe user ID and local date form the unique key.
Seven values, 0-4Zero is not felt; four is intense. Not zero to five.

Where does a saved check-in go?

Vercel hosts the web app. AWS verifies identity and persists only the authenticated user's records.

flowchart TD Cognito[Existing Cognito + Google SSO] -->|Access token| Web[React app / Vercel] Web -->|HTTPS + Bearer token| API[HTTP API / JWT authorizer] API -->|Verified user claims| Lambda[One check-ins Lambda] Lambda -->|IAM role| DB[(DynamoDB / CheckIns)] DB -->|Saved item or history| Lambda Lambda --> API API --> Web

Identity comes from the verified token. The client never chooses the owner of a database record. No AWS credentials, Cognito client secret, or Google client secret enter the browser.

A small, self-describing record

{
  "userId": "verified-cognito-sub",
  "date": "2026-10-07",
  "values": {
    "anger": 0,
    "frustration": 1,
    "worry": 2,
    "joy": 3,
    "sadness": 0,
    "guilt": 1,
    "fear": 0
  },
  "createdAt": "2026-10-07T15:00:00.000Z",
  "updatedAt": "2026-10-07T15:00:00.000Z",
  "schemaVersion": 1
}

Partition key: userId

The Cognito sub, derived by the server. Email is not a stable ownership key.

Sort key: date

A local calendar date, not a UTC creation timestamp. Updating the same day replaces its values instead of creating another record.

Server-owned timestamps

DynamoDB does not generate timestamps or enforce the feeling schema. Preserve createdAt with if_not_exists; update updatedAt on each write.

Use a map, not an ordered array

Use anger, frustration, worry, joy, sadness, guilt, and fear in the API and database. A repository adapter maps these to the current Portuguese app IDs without changing labels or local records. An array depends on a permanent order; adding or moving a feeling can silently change what old data means.

The smallest useful API

PUT /checkins/{date}Validate seven integer values, then save one day. Return the canonical item. Last successful server write wins.
GET /checkinsQuery only the current user's partition, in date order. Optional date bounds and paginated responses; never scan the table.
DELETE /checkinsPreserve the existing clear-all action only with confirmation and real remote deletion. Otherwise hide it in v1.

Save means the server accepted it

Keep the draft while the request runs. Disable duplicate submissions. Show the saved toast only after the response; retain input when a request fails.

Do not mix demo and real data

Sample records currently look exactly like real records. Isolate demo mode and require an explicit preview before importing local history.

Deletion is not a transaction

Clear-all needs paginated keys, bounded batch retries, and recovery from partial deletion. Concurrent writes on another device can create new records.

Could this be simpler?

HTTP API + Lambda

Recommended AWS-native path

Reuse Cognito JWT validation and Lambda's IAM role. One API, one function, one table.

More infrastructure than a Vercel Function, but no cross-provider AWS credential setup.

Vercel Function

Fewer deployed services

Keep DynamoDB and host the API beside the web app. Verify Cognito JWTs server-side with a proven library.

Needs least-privilege AWS access from Vercel, preferably workload identity federation.

Managed CRUD

Less handwritten API code

Amplify Data generates CRUD with Cognito ownership rules. Supabase or Firebase are also options for a different stack.

Amplify adds AppSync tooling; another platform needs an authorization integration or a change of auth stack.

Implementation, after approval

  1. Provision AWS resources. One on-demand table, a TypeScript Lambda, HTTP API, JWT authorizer, CORS, and narrowly scoped IAM.
  2. Implement GET and PUT. Strict dates and values, token-derived ownership, server timestamps, pagination, and explicit errors.
  3. Replace synchronous storage calls. Remote loading and confirmed saves; abort or ignore late responses when the account changes.
  4. Test real isolation and recovery. Two accounts, two devices, repeated daily edits, expired tokens, network errors, and partial deletion if enabled.

Initial boundaries

  • No automatic offline synchronization or silent local-data import.
  • No secondary indexes, VPC, separate user table, or stored summary data.
  • Emotional data stays out of application logs. Enable recovery, log retention, throttling, and alarms.
  • API, Lambda, database, logs, and backups have costs. Small serverless usage is not a promise of free hosting.
